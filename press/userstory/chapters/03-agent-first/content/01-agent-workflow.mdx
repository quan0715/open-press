## Agent-First 哲學

OpenPress 是一個建立在 **Agent-First** 哲學上的框架。這份文件說明整個系統的設計概念，讓你把思維從「自己寫程式的工程師」轉換為「指揮 Agent 的架構師」。

### 核心哲學：人做決策，Agent 執行

OpenPress 的核心前提很簡單：**你不應該自己手寫 JSX 元件，也不應該自己在終端機輸入 CLI 指令。**

- **人的角色**：提供意圖、品味、商業邏輯，以及審查最終輸出。你是這個專案的「總編輯」和「產品經理」。
- **Agent 的角色**：理解你的意圖，把它翻譯成精確的 React 程式碼和 Markdown（MDX）結構，並代表你執行所有建置和除錯流程。

你不需要記憶複雜的程式語法或設定步驟；這些繁瑣的實作細節會由 AI 自動處理。你真正需要掌握的，是整個系統的操作心智模型，以及如何清楚地向 Agent 發出指令。

### Skills：注入領域知識與品味

**Skill 是 Agent 的「插件大腦」和「品味過濾器」。**

- **賦予能力**：當你安裝了一個 UI 設計 Skill，Agent 就學會了如何使用特定的 CSS 框架來排版高品質的介面。
- **賦予領域知識**：當你安裝了 `documentation-writer` Skill，Agent 就學會了專業的技術寫作原則，能夠把雜亂的筆記重構成結構化的文件。
- **攜帶 Starter 範本**：很多 Skill 附有範本檔案。當你要求 Agent 建立一個新專案時，Agent 會讀取 Skill 裡的 starter 檔案，作為客製化你的專案的起點。

你可以把 Skill 想像成你聘請的「專業顧問團隊」，而 Agent 是負責協調並執行這些顧問意見的 CEO。

### 元件架構的心智模型

雖然你不需要自己寫程式，但你必須和 Agent 共享一套共同語言。OpenPress 把文件視為「元件樹」的三個基本層級：

1. **Workspace**：整個專案的宇宙。一個 workspace 可以包含多個不同的出版品。
2. **Press**：一份獨立的文件或簡報（例如一份 A4 提案，或一個 16:9 投影片組）。
3. **Frame**：頁面上的實體表面載體。有些是固定的（例如書的封面），有些則根據內容長度自動延伸成多個實體頁面（例如本文段落）。

### 為什麼放棄所見即所得

我們選擇使用 React 元件樹，因為 **AI Agent 特別擅長輸出精確、結構化的程式碼**。傳統的拖曳式編輯器很難用語音或文字指令精確控制，但透過結構化的 JSX，你只需要告訴 Agent：「幫我在這張投影片加一個雙欄比較圖」，Agent 就能完美產出對應的程式碼結構。

### 引擎的底層黑魔法

為了減輕使用者的認知負荷，OpenPress 底層引擎自動處理大量繁瑣的工程細節。你和 Agent 都不需要在這些事情上浪費時間：

- **自動路徑推導**：系統會根據資料夾名稱自動登錄路由和 `slug`（例如 `press/report/`）。
- **MDX 自動注入**：放在特定資料夾的 React 元件會被引擎自動暴露給 Markdown。當 Agent 寫 MDX 時，可以直接使用 `<Chart />` 而不需要處理繁雜的 `import` 路徑。
- **建置時定位器**：引擎在背景維護建置時的定位器，讓視覺介面和 source code 能夠互相對應，而不需要作者手寫定位器 props。

### 與 Agent 協作的實踐循環

1. **提供高層意圖**：「我需要做一個 10 頁的產品發佈簡報。請使用新安裝的品牌 Skill 確保統一的視覺風格。」
2. **讓 Agent 執行並建置**：Agent 會自動建立 `press.tsx`，生成對應的 MDX 內容，並在背景執行 `npm run dev` 為你啟動預覽。
3. **用評論標記做 review**：看到畫面上的預覽結果時，不要自己開編輯器修改程式碼。直接使用系統的「評論標記」功能。在你不滿意的地方框選並留言：「這裡字體太小」、「請把這段改寫得更專業」。
4. **閉環修正**：指令 Agent：「請解決畫面上的所有評論標記。」Agent 會精確地根據 ID 找到 source code 並修正所有問題。

### Agent 與框架的責任分工

框架本身極度被動。它不懂「美學」，沒有「說故事」能力，也不包含任何特定領域的商業邏輯。它的職責純粹是機械式的：解析元件樹、處理排版演算法、驗證結構正確性，並產生最終的靜態文件。

相反地，Agent 充滿觀點與主動性。透過不同的 Skills，Agent 可以扮演文案總監、視覺設計師，或技術文件專家的角色。

### Source Code 作為唯一真相來源

當 Agent 為你建立或修改文件時，所有變更都必須發生在 workspace 的「source code」層面。這是 OpenPress 設計中不可妥協的原則。

**為什麼不直接修改輸出？**如果 Agent 繞過 source code，直接修改編譯後的 HTML 或排版好的 PDF，那些修改會是脆弱且不可重現的。透過強制 Agent 只編輯 source code（例如 MDX 內容、React 元件，或 CSS tokens），我們確保文件的每一次修改都是宣告式的、可被版本控制追蹤的，並且能夠被引擎可靠地重新編譯。

### 邊界（Hard Stops）

雖然 Agent 很強大，但 OpenPress 設置了嚴格的邊界。Agent 被限制在文件建立的範疇；它不能任意修改框架的底層程式碼，不能憑空捏造商業指標，更絕對不能在未經明確授權的情況下把內容發布到公開的生產環境。這些邊界的存在，是為了在自動化和安全性之間取得完美的平衡。
